# custom-pr-reviewer

Audit a change against the pr-reviewer rules of liferay-portal and the stricter checks in this file. The goal is to answer one question before you send a pull request: **will the reviewer reject this?** Naming is the priority axis: a wrong variable, method, or class name is grounds to redo the pull request. The check covers the full catalog.

The **binding** rule catalog is `pr-reviewer/rules/` and `STYLE.md` in the repository (load them first, see the next section). The summary in this file gives orientation over that catalog.

## When to Use This Skill

Use it when the user invokes `/custom-pr-reviewer`, or asks for a custom pr-reviewer check, or asks to check a branch or a file against the pr-reviewer rules before a pull request. It is a *convention* check, complementary to `/code-review` and `/pr-check`.

## Load the Rule Catalog (first, on each run)

The repository contains the **authoritative catalog**: `pr-reviewer/rules/` and `STYLE.md`. Read them before the audit, so that each rule number, title, "A violation is…" definition, and example commit comes from the source, and so that this check follows changes of the catalog.

1. Find the repository root: `root = git rev-parse --show-toplevel`. The catalog is `${root}/pr-reviewer/rules/` (numbered `NNN-*.md`, families `0xx`–`9xx`) and `${root}/pr-reviewer/STYLE.md` (the philosophy and the formatter caveats). Git tracks them, so they are in each worktree.
2. Load the set in one pass (`cat ${root}/pr-reviewer/rules/*.md`), and audit the diff against each rule. Base each finding on the matching `NNN-*.md`: cite the exact number and title of that file, and use its violation definition or example. Read `STYLE.md` for the reasons and for the "Removing the unnecessary" judgment calls.
3. **Fallback:** if the directory is not there (not a portal checkout), audit only the checks of this file, and write in the report that the numbered rules were *not verified*.

This file does **not** repeat the numbered rules. It holds only what they do not contain: the mechanical pass, the priority axis, the stricter readings of some rules, the hard functional vetoes, the "AI slop" test, and the "Do NOT flag: the formatter wins" list. Where a repository `NNN-*.md` is more specific, **it wins**. Never cite a rule number that has no file under `pr-reviewer/rules/`.

## Scope Resolution

Find what to review, in this order:

1. **Argument given**: the user can give a file path, a directory, a ticket key (`LPD-12345`), or the literal `staged`.
   - File or directory → review only those, with `git diff $(git merge-base origin/master HEAD)..HEAD -- <path>`.
   - Ticket key → `git log --grep <ticket> --format=%H` to find the commits, then diff them.
   - `staged` → `git diff --cached`.
2. **No argument (default)**: review the current branch against master:
   - `merge_base` = `git merge-base origin/master HEAD`
   - `diff_files` = `git diff --name-only "$merge_base"..HEAD`
   - Diff of one file = `git diff "$merge_base"..HEAD -- <file>`

Give a one-line scope summary first (N files, N commits, base). If the diff is empty, say "Nothing to check." and stop.

**Skip generated files**: they contain `@generated`, `@Generated("")`, `$ANTLR`, `# This is a generated file.`, or `## Autogenerated`. A finding on them is noise. For REST Builder, the hand-written sources are `rest-config.yaml`, `rest-openapi.yaml`, the `*ResourceImpl.java` bodies, and the `*ResourceTest.java` bodies. All other files under `*-rest-api` and `*-rest-client` are generated.

For a large diff (more than about 15 files), send the analysis of each cluster of files to a subagent (one `Agent` call for each cluster) with the rubric below, then join the results. For a small diff, do it inline.

## The Mechanical Pass: Small Oddities (before you read the diff)

A reviewer looks for small oddities that a reader does not see in a long diff, for example a two-element `ArrayUtil.contains(new int[] {...}, ...)`. An LLM that reads 1,500 lines misses these, so a script finds the candidates and you judge each one. Run it first, with the base that you found above:

```bash
~/.claude/skills/custom-pr-reviewer/scan.sh "${merge_base}" HEAD        # committed branch
~/.claude/skills/custom-pr-reviewer/scan.sh "${merge_base}" WORKTREE    # include uncommitted edits
```

Each output line is `CHECK<TAB>file:line<TAB>excerpt`, only for lines that the diff adds, without generated files. **Each line must be in the report, as a finding or under Clean with the reason for the dismissal.** A candidate that you drop silently reaches the reviewer.

| Check | What it flags | Default verdict |
| --- | --- | --- |
| `JAVA_INLINE_ARRAY_MEMBERSHIP` | `ArrayUtil.contains(new int[] {A, B}, x)`, or `Arrays.asList(A, B).contains(x)` / `List.of` / `Set.of`, with 2-3 elements | **WARN.** An array allocated to compare a value with two constants is the over-engineered form. → `(x == A) \|\| (x == B)`. Put it in the surrounding condition instead of a negated membership test, so that the guard reads positively (accepted case → `return`, then `throw`). Keep `ArrayUtil.contains` only for an array that exists for another reason. |
| `JAVA_CHAINED_CALL` | a call on the value that another call returns, in main or test code: `foo.getBar().getBaz()` on one line, or the multi-line layout of the formatter with `).getJSONArray(` on its own line. The check skips statements that build a builder, a stream, an `Optional`, a `StringBundler`, a JSON object (`JSONUtil.`, `.put(`), a Mockito stub or verification, or a `java.time` value. It can therefore miss a chain in such a statement. | **WARN.** Rule 402, and stricter than its allow list: `_execute(...).getJSONArray("usages").length()` in a test is a violation, although `JSONObject` is on the 402 list. → assign each intermediate result to a named local (`JSONObject jsonObject = _execute(...);`, then `JSONArray jsonArray = jsonObject.getJSONArray("usages");`), as the sibling test does. Dismiss only a real fluent API that the exclusions did not catch, and name it under Clean. |
| `JAVA_RECEIVER_CALLS_UNSORTED` | a `set*`, `add*`, or `put*` call on a receiver before a later call on the same receiver whose method name sorts first, among the top-level statements of one method body, also when other statements are between them | **BLOCK.** Rule 202, applied past the contiguous block. See "Calls on One Receiver Sort Across the Whole Method" below. → move the earlier call down next to its alphabetical siblings, after the setup that the later call needs. Dismiss only a real dependency (the later call reads what the earlier one wrote), a generated model or REST DTO that follows the order of its `service.xml` or `rest-openapi.yaml`, or a search `Document` whose `add*` calls sort by field name. Name the reason under Clean. |
| `TS_TYPE_ASSERTION` | an `as <Type>` cast in added TypeScript (not `as const`) | **WARN (verify).** Check the target type: a cast to a type that the value is already assignable to (a string enum `as string` for a `{value: string}` prop) is noise. → delete it. Keep it only when the compiler needs it, and then say why. |
| `TS_CONDITIONAL_SPREAD` | `...(cond ? [] : [item])` or `...(cond ? [item] : [])` in an array literal | **NIT (verify).** It reads as a trick. → build the base array, and `push` or `unshift` the optional item under an `if`, as the same file does for options that a flag gates. |
| `UNGATED_LABEL_CHANGE` | a hunk that replaces a language key (`connect-sites` → `connect`) while the branch gates other parts of the feature behind a feature flag, and this hunk does not check the flag | **BLOCK (verify).** The flag is applied halfway: flag-off users see the new text for a feature that they do not have. Gate the label too, or show that the new text is correct without the feature. A hit in a hunk that only *adds* a message for a gated branch (the success message of the new kind) is a false positive: dismiss it under Clean. |

**Prove an oddity with a count, not a feeling.** For each construct that you suspect, flagged by the scan or not, measure its precedent in production code before you call it a convention or an oddity:

```bash
~/.claude/skills/custom-pr-reviewer/scan.sh precedent '<multi-line Perl regex>' ['*.java' | '*.tsx' ...]
```

A shape that 0-2 production files match has no precedent (Rule 001). Put the count in the finding (`ArrayUtil.contains(new int[] {two constants}) → 0 production files; 2 files use it with 3+ elements`).

**Read again each mechanical fix that you or another reviewer applied.** A review can produce an oddity: when Rule 502 inlines a `private static final int[] _ACCEPTED_TYPES`, it leaves an inline array literal behind. When a rule rewrites code, judge the result as new code. When an inlined value leaves an odd shape, rewrite the full expression instead of the value only.

## The First Cut: Is the Order Random?

Random order (Rules 201–209) is the **most frequent cause of rejection**, and a reviewer stops at the first violation. Check the ordering rules before all other rules, and apply them **also to generated template or CLI output** that the branch writes. One unsorted sequence alone is a probable rejection.

### Calls on One Receiver Sort Across the Whole Method

Rule 202 sorts "a contiguous block of setter calls on one object". Apply the sort to each call on that receiver in the method, also when a setup block is between them. Setup that only one call needs does not let the calls before it stay out of order. Move each call down to its alphabetical position, after the setup that the later call needs, so that all calls on the receiver are in sorted order.

The sort moves the calls, never the setup. A setup block (a local and its own calls, such as `ThemeDisplay themeDisplay` and its `set*` calls) stays immediately before the one statement that consumes it, as Rules 203 and 909 require. Do not move the setup block above the first call on the receiver to put all calls in one paragraph: that moves a declaration away from its use. A call that sorts before the consumer of the setup stays above the setup block. A blank line between calls to two different methods on the receiver (`setAttribute`, then `setParameter`) is a Rule 909 group separator, not a collapse candidate. The collapse scan joins only calls to the same method.

```diff
 mockLiferayPortletRenderRequest.setAttribute(
 	StringBundler.concat(
 		mockLiferayPortletRenderRequest.getPortletName(), "-",
 		WebKeys.CURRENT_PORTLET_URL),
 	new MockLiferayPortletURL());

-mockLiferayPortletRenderRequest.setParameter(
-	"classNameId",
-	String.valueOf(_portal.getClassNameId(BlogsEntry.class)));
-mockLiferayPortletRenderRequest.setParameter("classTypeId", "0");
-
 ThemeDisplay themeDisplay = new ThemeDisplay();

 ...

 mockLiferayPortletRenderRequest.setAttribute(
 	WebKeys.THEME_DISPLAY, themeDisplay);

+mockLiferayPortletRenderRequest.setParameter(
+	"classNameId",
+	String.valueOf(_portal.getClassNameId(BlogsEntry.class)));
+mockLiferayPortletRenderRequest.setParameter("classTypeId", "0");
+
```

The Blank-Line Collapse Scan misses this case, because the calls are not contiguous. The mechanical pass flags it as `JAVA_RECEIVER_CALLS_UNSORTED`. Treat a hit as **BLOCK**, and fix each hit in the diff, not only the first one.

### The Blank-Line Collapse Scan (mechanical, BLOCK tier: run it on each diff)

The most frequent correction on this axis is not a list that is visibly out of order. It is a **blank line between two consecutive statements of the same kind**, because that blank line hides the unsorted block. In each method body that the diff touches, find two statements with **only a blank line** between them (no statement between them), and collapse them:

- **Two local declarations** → one block: delete the blank line **and** sort alphabetically by variable name (201/202). The variable name gives the order, not the type.
- **Two calls to the same method, or two consecutive `Assert.*` assertions** → one block: delete the blank line. Keep the existing order, unless the argument tuples give a real sort key.

**The blank line of Rule 203 separates a declaration from the statement that consumes it. It never allows a space between two declarations.** A blank line between two declarations does not exempt them from 201: it is the violation.

Four cases keep the blank line:

1. **Derived**: the second statement is calculated from the first (`Layout masterLayout = _layoutLocalService.getLayout(...);`, then `UnicodeProperties typeSettingsUnicodeProperties = masterLayout.getTypeSettingsProperties();`). 201 keeps a derived assignment out of the sorted block and next to its use.
2. **Burrito wrapper**: the first is the value that the method returns, or a local whose **only purpose** is to receive another local through a setter (`StyleBookEntry styleBookEntry = null;` … `return styleBookEntry;`). 203 declares it first and closes with the return or the setter call. Read "only purpose" strictly: a container that already carries its own content, is changed, and is written back is an ordinary peer, not a wrapper. `UnicodeProperties typeSettingsUnicodeProperties = layout.getTypeSettingsProperties();` next to `String themeSettingValue = RandomTestUtil.randomString();` collapses and sorts (`themeSettingValue` first), although the `put(key, themeSettingValue)` after them looks like a setter that closes a burrito. The test: does the local exist *only* to hold the other one?
3. **Observed side effect**: a swap changes the behavior, because the second statement observes what the first did (`_updateLookAndFeel(group, themeId);`, then `Layout layout = _getLayout(...);`).
4. **`MissingEmptyLineCheck` requires it: the formatter wins.** This case applies only to the *statement and assertion* half of the scan, and it overrides the collapse. Checkstyle's `MissingEmptyLineCheck` requires an empty line after the statement that holds the **last reference to a local declared above it**, so this pair cannot collapse:

   ```java
   Theme layoutSetTheme = layoutSet.getTheme();
   Theme layoutTheme = layout.getTheme();

   Assert.assertEquals(
       layoutSetTheme.getThemeId(), layoutTheme.getThemeId());
                                          // ← empty line REQUIRED here:
                                          //   layoutSetTheme/layoutTheme end above
   Assert.assertEquals(
       layoutSet.getThemeSetting(key, "regular"),
       layout.getThemeSetting(key, "regular"));
   ```

   **The way out: sort the pair.** The check looks at *position*, not at the collapse. When the alphabetical order of Rule 202 puts the last-reference statement **last**, the pair collapses and `formatSource` passes. Try that before you keep the blank line. For example, `Assert.assertEquals(layoutSet.getCss(), ...)` sorts before `Assert.assertEquals(layoutSetColorScheme.getColorSchemeId(), ...)` (`layoutSet.` < `layoutSetC`, because `.` is `0x2E`): the sort orders the block and allows the collapse. It fails only when the sort puts the last-reference statement first (expected value `layoutSetTheme.getThemeId()` before a local named `themeSettingValue`). There the blank line stays, because the order is more important than the collapse. Never reorder against the sort to collapse a pair.

   **Declaration pairs go through a second branch of the same check** (`empty.line.missing.before.variable.assign`). It is the mechanical form of Rule 203, and it decides if two declarations are one block. Read `_checkMissingEmptyLineBeforeVariableAssign` in `modules/util/source-formatter/.../checkstyle/check/MissingEmptyLineCheck.java`. For a block of adjacent assignments, it collects the identifiers that the **statements after the block** use. If an assignment that those statements *do not* reference comes before one that they *do* reference, it requires an empty line before the referenced one. So:

   - both consumed by what follows → one block, collapse and sort (`Group designLibraryGroup` and `JournalArticle journalArticle` used by `_addDisplayPageTemplate(...)`);
   - only the **first** consumed → no problem, the check returns early;
   - only the **second** consumed → **blank line required**, and the correct fix is 203: give that declaration its own paragraph immediately before the statement that uses it.

   When the check fires, the two declarations are not peers. Move the declaration instead of a forced collapse.

All other pairs collapse. Two independent fixture declarations are one block **also when their first uses are far apart**: the `_addX()` setup at the start of a test method is one sorted block, not one paragraph for each fixture.

Treat a hit as **BLOCK**, not as a nit: this is where a reviewer stops. `formatSource` does **not** flag the declaration case (`JavaEmptyLinesCheck` has no such check), so this scan is its only gate. Run it to zero before you send a pull request. Then run `formatSource`, and let case 4 decide the statement pairs. When `formatSource` expands a collapse again under case 4, explain this in the pull request instead of a silent revert.

## Naming: The Priority Axis

A single wrong name can cause a request to redo the full pull request. Check **each** new or renamed class, method, and variable against the naming rules (101–114) and against all points below. Each finding cites the rule and gives the correct name.

### Variables / fields

- **Container-type suffix (a hard source-formatter rule).** A variable of type `Map` has the name `*Map`, never a name from its key or role: `countsMap`, `pageExperiencesByKey` → `pageExperiencesMap`. `formatSource` applies this rule, so fix it, or the formatter fixes it for you.
- **A content or format suffix must be true.** A `String` that holds serialized JSON takes a `JSON` suffix (`filters` → `filtersJSON`, `classNameToBackgroundTaskJSONString`). But never attach a `*Schema`, `*JSON`, or `*String` qualifier to a value that is not that: what is the difference between a `bodySchema` and a `body`? The suffix names the real content, not a guess.
- **Never shorten, hide, or drop a prefix.** If the convention is `_getPortletURLString`, do not change it to `_getURL`.
- **One identifier, one meaning, and one meaning, one identifier.** A variable must not use the name of a domain class (`String groupBy` collides with the class `GroupBy`; `String resource` suggests `model.Resource`), and one concept must not have synonyms. Examine the full class, so that one thing has only one name, and no other thing has that name. Rename ambiguous short names when two domain types exist (`Order` → `PlacedOrder` or `CommerceOrder`: choose the exact one). Do not add a new term for a concept that already has a name. (Extends Rule 104: one variable cannot mean two different things.)

### Methods

- **Methods start with a verb.** `cachedX()` → `getCachedX()` / `fetchX()`.
- **A rename that still hides the real thing is still wrong.** Verify a name against the literal data or markup (an `<index>` element is not a `SitemapIndex`). Name a getter by its concrete return type when no class has the abstract noun: `getActiveProfile()` → `getActiveKeyManagerProfile()`, because there is no `Profile` class.
- **A boolean name must have a clear meaning and polarity** (extends Rule 102). `isProvidesContent` is confusing (`isEnabled` or `hasContent`?). Use `isEnabled` or `isDisabled` consistently.

### Classes / tests

- **Abstract bases have the `Base*` prefix.**
- **Do not give a concept the wrong name**: do not call something a "framework" when it is not one, and do not make a typo in a product name.
- **Name a REST exception mapper after the REST Builder DTO, never the Service Builder entity.** A `ProblemMapper` or `ExceptionMapper` uses the API vocabulary: `UtilityPageNameExceptionProblemMapper` maps `LayoutUtilityPageEntryNameException`, and `SiteKeyExceptionProblemMapper` maps `GroupKeyException`. `DuplicateLayoutPageTemplateEntryNameExceptionProblemMapper` is wrong: use the REST Builder DTO name. When one entity is behind several DTOs (`LayoutPageTemplateEntry` is behind `MasterPage`, `DisplayPageTemplate`, and `PageTemplate`), use the name of one DTO, as `DisplayPageTemplateMarkAsDefaultExceptionProblemMapper` does also for master pages. Older mappers with the entity name (`RequiredLayoutPageTemplateEntryExceptionProblemMapper`, `LockedLayoutExceptionProblemMapper`, `RequiredLayoutContentVersionExceptionProblemMapper`) are not a precedent to copy. Flag a new mapper with an entity name as BLOCK. (Sharpens Rule 001.)
- **A new util cannot take the unprefixed name when siblings exist.** When many classes already share a base name (`FriendlyURLUtil` is in about 6 places), a new one must have a prefix that groups it.

### Service Builder entities & columns (service.xml)

- **An entity name must have the namespace word of the module as prefix, never a bare noun.** In `segments-service`, the entities are `SegmentsAaa`, `SegmentsBbb`. `com.liferay.journal` cannot have an entity named only `Journal` (it is `JournalX`, `JournalY`). `layout-content-versioning` cannot have `LayoutContentVersion` as a bare entity.
- **service.xml column names must tell what each column stores.** Vague names are a violation.
- (Ordering and the `short-no-such-exception-enabled` flag are under "Liferay-Specific Conventions" below.)

### Product names, casing & constants

- **Use the house abbreviation pattern for product names, and choose ONE short form.** Do not write `seoStudio`, in the same way that the code does not write `aiHub`. When you choose `GSC`, do not also write `Google Search Console`. Keep identifiers and JSON keys consistent (`pageSpeedScan` next to `pagespeed-object-action-scan` is a violation).
- **Brand and product names use their official casing**: `oras` → `ORAS`, `helm` → `Helm`, in identifiers, labels, and CI step names.
- **Spell out environment qualifiers, without abbreviations, hyphens, or underscores.** Use `NONPRODUCTION`, not `NONPRD`, `non-prd`, `non_prd`, `NONPROD`, or `NON_PRODUCTION`, and never let two variants exist together.
- **Name a constant after the exact slot that it represents**, so that the family can grow: `ATTRIBUTE_*` → `ATTRIBUTE_NAME_*` (with space for `ATTRIBUTE_VALUE_*`). If the constants add nothing, delete them.

### Test methods

- **Sub-scenarios under one consolidated `@Test` get a numeric-suffix helper family** named after the test method: `_testGetSiteSitePageRenderedPage123()`, `_testGetSiteSitePageRenderedPage456()`, `_testGetSiteSitePageRenderedPage789()`. And **merge sibling single-assertion `@Test`s that test the same method** into one (`testGetOptionsRequiresBody` + `testGetOptionsSetsJSONContentType` → `testGetOptions`). (Sharpens Rule 605 / 601.)
- **A sibling family uses one qualifier scheme, and each qualifier copies the identifier that it represents.** When two or more helpers, tests, or locals are different only by a qualifier, the qualifier is the exact name of the fixture or variable that makes the scenario different, with all of its prefix words. Each member of the family follows the same scheme. Do not drop a prefix word on one member, and do not use a synonym on another member (`Site` when the code says `group`). Example of a violation:
  - `_testContributeWorkflowContextWithDesignLibraryDefaultDisplayPage()` next to `_testContributeWorkflowContextWithSiteDefaultDisplayPage()`.
  - The fixtures were `_addConnectedDesignLibraryGroup()` and `_group`. The locals were `designLibraryGroup` and `designLibraryLayoutPageTemplateEntry` next to a bare `layoutPageTemplateEntry`. The precedent `AssetDisplayPageUtilTest` names its scenario `testHasAssetDisplayPageWithConnectedDesignLibraryGroup`.
  - So `DesignLibrary` dropped `Connected`, and no identifier of the branch used the word `Site`. The scheme of the locals (prefix on the Design Library side, nothing on the own-group side) did not reach the helper names.
  - → Rename both members from the same source, for example `…WithConnectedDesignLibraryGroup()` and `…WithGroup()`. When the scenarios are only steps of one test, the numeric family above is also correct.

  **Procedure (mandatory).** For each family of two or more added names with a shared stem, write the map `qualifier → identifier it copies` in the report. Report it as **BLOCK** when a qualifier has no source identifier, drops a word that its source has, or uses a different scheme from its siblings (one member with a prefix, one with a synonym). Also compare the family with the qualifiers that the same branch uses on the locals for the same two scenarios. A family that passes goes under Clean with its map. (Extends Rules 106, 112, and 001 to the qualifiers of test helpers.)
- **The test-method name must map to a method that exists on the subject class.** Verify it with grep. `testEscape` is correct if `Field#_escape` exists. `testDecodeDefaultValueCollection` is wrong if there is no `decode` method, and `testEmit*` is wrong if there is no `emit` method. A name with no matching method is a violation. It must map to a **method that the test calls**, not only to options or configuration. (Sharpens Rule 603.)

## Beyond the Numbered Rules

These are stricter readings of some numbered rules, and checks that the catalog does not contain. Cite the rule that a point extends when it names one.

**Consistency (extends 001 / 002)**
- If you rename a thing in `InputGuardrailImpl`, rename it also in the sibling `OutputGuardrailImpl`: both or neither. Regenerate artifacts, and never delete a test without a replacement.
- **A pattern with no precedent is itself the smell.** An inline Gradle `test { jvmArgs "--add-opens" ... }`, a custom build or configuration form, or a hand-written argument scheme must match an established sibling. Do not invent a new one. Feature-flag descriptions must also match the grammar of the existing descriptions.
- **Parameter order must be consistent across sibling and overloaded methods.** `getSitemap(... int page, ..., ThemeDisplay themeDisplay)` next to `getSitemapInputStream(... ThemeDisplay themeDisplay, int page)` is a violation: make the position of `page` and `themeDisplay` the same in all of them.

**Ordering (extends 201–209)**
- **Sort instead of line breaks.** The mechanical form is **"The Blank-Line Collapse Scan"** above. It is BLOCK tier, and `formatSource` does not catch it.
- **Alphabetical order is better than "importance".** An order by importance is not obvious, so the next person adds an item in the wrong place, and then nobody knows the order.
- **Sort all that you can sort**, also individual conditional checks and exception-class arguments. Examine each line for consistency.

**Platform idioms (extends 3xx)**
- **303 does not allow an array for a few constants.** A test of a value against 2-3 fixed constants is a `==` chain. `ArrayUtil.contains(new int[] {A, B}, x)` is the over-engineered form (see "The Mechanical Pass").
- **`MapUtil.forEach(map, (key, value) -> ...)`** instead of a hand-written loop on the entries or keys of a map.
- **`Validator.isNull` is for Strings only.** Replace a hand-written `s == null || s.isEmpty()` on a `String` or `CharSequence` with `Validator.isNull(s)`, but use plain `== null` for other references (enums, objects).
- **A feature-flag-gated `*LocalServiceImpl` override that duplicates the generated method must call `super`**, so that you can delete the hand-written method when you remove the flag. Do not fork generated logic permanently.

**Control flow (extends 4xx)**
- **402 applies also to `JSONObject` and `JSONArray` results**, although the 402 allow list names them: `_execute(...).getJSONArray("usages").length()` is a violation. Only a chain that builds the JSON (`JSONUtil.put(...).put(...)`) is fluent. Look for `service.getList(...).size()` in an assert. The mechanical pass flags these as `JAVA_CHAINED_CALL`.
- **Put a builder local into one fluent chain**: `_factory.create().user(...).build()`, not `Builder builder = _factory.create(); ... builder.build();`.
- **No loops of loops.** Split nested iteration into separate methods.
- **Remove an unnecessary `finally`.**

**Inlining (extends 502)**
- After you inline a constant, **judge the expression that results.** A constant array inlined into `ArrayUtil.contains(...)` leaves an inline array literal, which is worse than the constant. Rewrite the full condition (a `==` chain) instead of the value only.
- Inline a **`private` method that has exactly one caller** (for example `_publishInitialRelease`, `_registerDocumentBuildCounter`, `_hasManagePermission`), unless it makes the code much easier to read.

**Tests (extends 6xx)**
- Put identical sleep or wait blocks (with their comments) that *separate* test files duplicate into one shared place.
- **LocalService add and update tests use the fast, newer pattern:** one positive `@Test`, and a separate `@Test(expected = ...Exception.class)` for each validation case (as the object and list-type-entry tests do), so that the tests run faster.
- **Use `@Ignore` consistently and with a reason** across overridden tests: an empty disabled `@Test {}` needs the same `@Ignore` (with a reason) as its siblings, not a silent empty body.
- **Use the house test pattern, not a custom harness.** The house pattern also lets you replace parts with mocks.
- Change a repeated *asserted* literal to a named constant.

**Prose (extends 7xx)**
- A message in production code and its asserted copy in a test must have the same punctuation.
- **Delete section-header comments that only repeat the name.** A `// Audience entry` banner in `AudienceEntryLocalServiceImpl` adds nothing.

## Hard Functional Vetoes (the BLOCK tier)

These are the most serious findings. The numbered rules do not cover them, so check them manually. Always cite the source that sets the contract.

- **Cross-file semantic contracts.** A value that a regex or parser in another module validates. Example: the `className` hashes of `ObjectDefinition` must match `[a-zA-Z]\d[a-zA-Z]\d`, and `ObjectDefinitionClassNameProcessorImpl` enforces this. If the diff writes a value that another part of the code parses, find and check that parser.
- **Wrong API or permission.** For example, `discussionPermission.hasUpdatePermission` where a different check is correct, or a call to `TransactionInvokerUtil` from a `*LocalServiceImpl` (wrong in about 90% of cases).
- **Architectural placement.** Logic in the wrong layer, for example in `PortalImpl`.
- **A new copy of an existing utility** instead of the existing one (an alter column type, `isNullOrEmpty`, and similar).
- **Fake or placeholder implementations**: code that looks complete but does nothing real.
- **Dead or unused code.**
- **A local or instance JVM `Map` used as a "cache" does not work in a cluster.** If the state must be shared, it needs a real distributed cache, not an in-process map.
- **Heavy work at portal startup** makes startup slow, and core infrastructure will probably revert it. Flag all expensive logic that runs at boot.
- **Wrong dependency-injection style in portal modules.** Do not add Spring `@Service` beans or `@Value` constructor injection. Use the existing pattern: OSGi `@Component` and `@Reference`.
- **Redundant hand-written permission or identity check.** A manual `companyId == permissionChecker.getCompanyId()` or a private `_hasManagePermission` wrapper is wrong when `ModelResourcePermission.check(...)` or `PortletResourcePermission.contains(...)` already enforces it. Use the existing check.
- **`TransactionInvokerUtil` in application or import code**, not only in a `*LocalServiceImpl`. A `LayoutImportCallable` wrapped in it is suspicious: send transaction handling through core infrastructure.
- **A feature flag applied halfway.** When the branch gates a feature behind a flag (`FeatureFlagManagerUtil.isEnabled`, `Liferay.FeatureFlags[...]`), each user-visible change that makes sense only with the feature (renamed labels, titles, empty states, menu entries) must be behind the same flag, or none must be. If the empty-state description is gated but the title, the menu label, and the section header change for all users, flag-off users see text for a feature that they do not have. Also, when the flag goes away, there is no single place to delete. The `UNGATED_LABEL_CHANGE` scan finds the candidates. Follow each one to the screen where it shows.
- **Parallel constant sets with conflicting values are misleading.** A new `JournalSearchConstants {SINGLE=1, FRAGMENT=2}` that is different from the sibling `DLSearchConstants {MULTIPLE=0, SINGLE=1, FRAGMENT=2}` is misleading. Use the existing constants or literal values. Never fork a conflicting set.

## Noise / "AI Slop"

Code that looks generated is a cause of rejection. Flag it, and use the simpler form:

- Unused code and new copies of existing utilities.
- Over-nested lambdas: call a method instead.
- **Unnecessary `final` on ordinary locals.** Do not add `final` to local variables.
- Round-about ways to do something simple. Treat AI output as a draft that you must rewrite until it does not look generated.
- **Machinery that is too large for the job**: an array allocated to compare with two constants, a type assertion that the compiler does not need, a conditional spread to add one optional item, a generic type parameter added to a base class to change one return type. Each one is small, but together they show that nobody examined the pull request carefully. The mechanical pass finds the common shapes. For the rest, ask for each added construct: is the plainest form that a Liferay developer writes by hand shorter?
- **Over-engineered schemes look generated**: a complex argument pattern, or inefficient round-about data plumbing (chains of list↔set conversions, transforms, and filters to merge collections). Simplify them.

## Liferay-Specific Conventions

**Service Builder / service.xml**
- **Column sequences match the `service.xml` order**, which has the groups `<!-- PK fields -->` → `<!-- Audit fields -->` → `<!-- Other fields -->` (alphabetical in "Other"). Assertions, getters, and setters use that order. Sort the columns in `service.xml` too.
- **New entities declare `short-no-such-exception-enabled="false"`**: follow the newer Service Builder pattern.
- (Entity and column *naming* are under "Naming" above.)

**Shell scripts (`.sh`, CI YAML)**
- **Name shell variables with `_`, not `-`.**
- **Find the script directory with `cd "$(dirname "${BASH_SOURCE[0]}")"` at the top, then use relative paths** for all files. Do not calculate a redundant absolute-path variable such as `_SCRIPTS_DIR=$(cd ...)`.
- Put repeated shell code into `_common.sh`.

**Client extensions**
- **Directory names follow `workspaces/liferay-sample-workspace/README.md`.** `liferay-seostudio-gsc` is a wrong directory name. Read that README for the convention before you name a client extension directory.

## ⚠️ Do NOT Flag These: the Formatter Wins

The Liferay source formatter reverts this `STYLE.md` simplification, and the formatter is authoritative. Never report it. If you see code in the *named* form, that form is **correct**: do not change it. (`STYLE.md` already has the redundant-boolean caveat.)

- **`inline single-use local` when the local is the operand of a binary operator.** `Checkstyle:OperatorOperandCheck` requires the right-hand operand of `-`, `+`, and similar operators to be a *named* variable. So `int suffixLength = ...; x.length() - suffixLength` must keep `suffixLength`. An inline of a single-use local is safe only when its one use is **not** the operand of a binary operator.

Also: **for a generated DTO that `extends` a base** (extends Rule 202), setter calls go **inherited base-class fields first (alphabetical among them), then the fields of the subclass (alphabetical among them)**. The base fields are grouped first, not mixed. (This overrides the general rule to sort setter calls alphabetically for generated DTOs.)

## Output: the Report

Give one markdown report. Start with an estimated rejection risk, then the findings grouped by severity. Each finding cites the rule and `file:line`.

```markdown
# custom-pr-reviewer: <scope summary>

**Estimated rejection risk:** <LOW | MEDIUM | HIGH> — <one-line reason>
(Only a direction: a clean pass does not guarantee the merge, and HIGH is not a certain rejection. Order and naming give most of the signal.)

## BLOCK (N) — the pull request will be closed or redone
- **[Rule NNN | functional veto]** `file:line` — <finding>. → <fix>. <source contract, if functional>

## WARN (N) — ordering, naming, noise
- **[Rule NNN]** `file:line` — <finding>. → <fix>.

## NIT (N) — prose and format; formatSource fixes most of these
- **[Rule NNN]** `file:line` — <finding>. → <fix>.

## Clean
- <checks that passed, so that the user knows they ran, especially "ordering: OK" and "naming: OK">
- <mechanical pass: N candidates, each one dismissed here with its reason when it is not a finding above>
```

Severity mapping:
- **BLOCK**: a wrong variable, method, or class name; a blank line between two statements of the same kind (the collapse scan); a broken established pattern; a hard functional veto (a feature flag applied halfway included); dead or unused code.
- **WARN**: random order, other naming problems, missed platform idioms, noise, problems in test values or structure.
- **NIT**: only prose or format (701–708, 902, 904, 905, 906, 908). `formatSource` applies many of these.

Keep findings short and concrete: name, `file:line`, and the correct form. Do not pad. If a check is ambiguous, mark it `(verify)` instead of an assertion.

## Then Offer to Fix

After the report, if there is at least one finding with a fix, ask with `AskUserQuestion`:

- One multiSelect question: *"Which findings should I fix now?"*, with one option for each BLOCK or WARN finding that has a concrete, mechanical fix (label = `[Rule NNN] short title`), and "Fix all mechanical", "Skip all".
- Apply only the selected fixes with `Edit`. Skip judgment-call findings (naming by intent, architectural placement) unless the user selects them: those often need the domain knowledge of the author.
- **Never apply a simplification that the formatter reverts** (see "Do NOT Flag These"), and never edit generated files.
- After the fixes, if the diff touches Liferay modules, suggest `gw formatSource` (or the `format-source` skill), so that the remaining source-formatter nits are fixed before the pull request. Otherwise they come back as a separate `<TICKET> SF` commit.

## Before You Send the Pull Request

- Order is the first cut: a reviewer stops at the first random sequence.
- **Small pull requests, smaller than you think.** Send prerequisites first, in a separate pull request. Rebase clean. If you do not know the standards yet, ask a teammate who knows them to review the pull request before you send it.
- Vendored or synced code goes in one traceable commit ("X came from Y").
- Be confident on the mechanical findings, and mark the others `(verify)`.
